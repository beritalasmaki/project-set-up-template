# Problem statement checks

Use after drafting the problem statement. Do not skip them.

## The solution check

A problem statement should describe a situation, not a thing to build. Read it and ask:

- Does it contain a thing to build? Words such as *new form*, *dashboard*, *app*, *portal*, *page*, *button*, *tool*, *chatbot*, *redesign*, *progress bar*.
- Could it be answered by "yes, we will build that"? If so, it is a request, not a problem.
- Could three quite different designs all solve it? If not, a solution is hiding inside.
- Does it say who is stuck, doing what, and why?

If any answer points to a solution, rewrite the statement as: *[who] is trying to [do what] but [what gets in the way], which leads to [consequence].*

## Example of the shift (fictional)

- Request: "We need a new online form for building permits."
- Hidden solution: *a new online form*.
- Problem: "Home owners applying for a permit do not know what the municipality needs from them, so they submit incomplete applications and wait weeks for a reply."

## Questions to ask the designer when evidence is thin

- Who has seen this problem happen? When, and how often?
- Is there any data (volumes, returns, calls, complaints) or only an impression?
- Who is affected that the request does not mention?
- What happens today when someone hits this problem?
- What would make this not worth solving?

## Hypothesis check

- Is each hypothesis testable, with a way to find out?
- Is any hypothesis really a solution in disguise?
- Is the riskiest one (high risk, high value) the one tested first?

## Honest status

- A problem framed from opinion alone is a draft. Say so at the top.
- `baseline needed` is a good answer. An invented target is not.
